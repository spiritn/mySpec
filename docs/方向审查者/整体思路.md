# mySpec 个人开发方法论 · 整体思路

## 当前判断

用户已明确采用三个独立代码评审角度：需求与逻辑正确性优先，另审架构规范和性能；问题分级，先理解需求，再用真实场景和代码证据说明影响。

已在本地写入三个角色、共享 review Skill、举证细则与调用入口。用独立上下文隔开初判，由主会话核对场景、去重和汇总。等级与证据状态分开，不把极端假设或术语堆积当深入。已完成配置检查、隔离快照和一次真实变更的三专项试跑，尚无方法效果对照；本次暂不增加安全专项。

## 目标与背景

把反复口头交代的做事标准，沉淀成符合个人习惯、可持续改进的开发流程。主要服务个人和公司的日常需求开发，跨项目复用是结果之一。

原始来源为 2026-11-21 本聊天：用户强调“重点是……符合我个人习惯的……可复用的一套方法论”“不想把这些话重复地去说”，希望在已有主 Skill 引用阶段 Skill 的框架上完善。随后明确选择第一轮聚焦“代码评审：审得深入、讲清依据和影响”。本轮进一步要求三个独立角度、独立上下文和问题等级，优先需求实现完整性、真实影响与易懂表达；架构检查要结合项目规范，性能检查要结合实际工作量。安全专项暂不纳入。另一台电脑上的原始框架尚未读取，不推定其内容与本仓库完全相同。

用户已明确的表达习惯：普通中文；复杂问题先交代背景和整体思路；保留判断所需的事实、数字、取舍及限制；避免术语堆积和执行流水账。不能为了简短而删掉关键原因。

成功应表现为：同类任务少重复交代，产出更稳定，重要遗漏和无依据结论减少，用户更容易作出判断。角色数量、提示词长度和文档数量不能证明有效；具体验收门槛尚未确定。

## 方案调研

现有框架已有开发流程骨架。公开资料支持先沉淀重复方法、按需要分工并验证结果；这些是设计参考，不是本项目已有效的证据。

### 当前 mySpec

[workflow](../../skills/workflow/SKILL.md) 已负责范围、阶段衔接、续跑和返工；[design](../../skills/design/SKILL.md) 已覆盖需求澄清与技术方案；[task](../../skills/task/SKILL.md)、[code](../../skills/code/SKILL.md)、[review](../../skills/review/SKILL.md)、[complete](../../skills/complete/SKILL.md) 已覆盖拆解、实现与自查、评审和归档。验收编号、代码证据、上下游影响、验证结果与未决事项已有约定。

代码评审 Skill 已要求独立评审、明确版本、追踪调用方与契约、用触发条件和证据说明风险，也有[评审反馈与评估方法](../../skills/review/references/advanced.md)。这些约定是否实际减少用户纠正，当前材料不能回答。覆盖所有阶段的个人反馈迭代办法尚未明确，是否为首要瓶颈仍需真实使用验证。

### OpenAI：重复工作沉淀为 Skill，主会话保留全局任务

官方[最佳实践](https://learn.chatgpt.com/guides/best-practices)建议用目标、上下文、约束、完成条件说明任务，把稳定指导和重复工作沉淀下来。[子 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)说明独立上下文可隔离探索细节，主会话汇总结果；并行写入需要注意协调成本。以上于 2026-11-21 查阅官方手册，不据此假设本次所有角色入口均可调用。

### Anthropic：按任务选择工作流和多 Agent，并从小规模真实样本开始评估

[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents?spm=a2c6h.13046898.publish-article.12.2dbf6ffaplwDfR)分别介绍串联、分流、并行、协调者与评估改进等模式；选择应依赖任务特点。[多 Agent 研究系统经验](https://www.anthropic.com/engineering/multi-agent-research-system)提醒共享上下文与相互依赖会增加多 Agent 协作难度，并建议从少量真实任务开始评价结果。其研究系统经验不能直接证明日常编码采用多 Agent 更好。查阅：2026-11-21。

## 整体方案与进度

保留 workflow 和阶段 Skill。个人表达要求、阶段做法、项目规则分别维护；只在确需独立判断、隔离大量细节或可独立并行时增加 Agent。

| 工作 | 当前建议分工 | 交接重点与状态 |
| --- | --- | --- |
| 组织流程 | 主会话使用 workflow | 保存原始目标、当前决定和版本；现有能力 |
| 需求澄清与方案设计 | 使用 design，暂不预设两个新 Agent | 用户需求、现状证据、验收、取舍和待定项；具体改进待试点 |
| 任务分解 | 使用 task | 验收覆盖、依赖和每项完成条件；现有能力 |
| 编码与自查 | 使用 code；有独立写入范围时再委派 | 实际改动、测试结果和剩余问题；现有能力 |
| 代码评审 | 三个独立评审角色调用共享 review Skill | 用户已确认角度与独立上下文；角色已写入并链接；配置和一次真实变更试跑完成，效果对照未做 |
| 方向审查 | 现有两位方向审查者 | 用于重要方向或投入选择，不作为所有小任务的必经步骤 |

建议保留的主链路如下，不表示已经验证了新流程效果。

```mermaid
flowchart LR
    A[用户需求] --> B[需求与设计]
    B --> C[任务分解]
    C --> D[编码与自查]
    D --> E[独立代码评审]
    E --> D
    E --> F[交付与反馈]
    A --> G[按需方向审查]
    G --> B
```

### 第一轮：三个独立评审者

先理解同一份原始需求与代码版本，分别形成初判；需求完整性最重要。分角度不能变成三个 Agent 各凑一份问题。

| 角色 | 主要判断 |
| --- | --- |
| [需求与逻辑](../../agents/code_review_functional.toml) | 需求一句话能否讲清、核心流程是否完整、真实边界、历史数据是否需处理、其他模块及旧行为是否受影响 |
| [架构规范](../../agents/code_review_architecture.toml) | 现行模块划分、类与方法职责、依赖及复用；设计原则必须解释具体维护后果，不能为模式而重构 |
| [性能](../../agents/code_review_performance.toml) | 在有依据的使用规模下，查询、计算、外部调用、批量更新、内存和并发成本是否有实质问题 |

角色定义职责，共享 [review Skill](../../skills/review/SKILL.md) 定义方法，[举证细则](../../skills/review/references/angles.md)按需展开。各自读取原始资料，不看同行初判，不递归调度，不修改业务代码；主会话汇总与安排修复。不是新增三个相互复制的长 Skill。

### 等级、证据和报告

后果严重程度分高、中、低；是否已查实另行表达。低频但有可达路径且后果严重的问题仍需报告，不因低频而忽略。

| 等级或状态 | 含义 |
| --- | --- |
| 高：必须处理 | 核心需求缺失、关键行为错误、数据丢失或不一致，或违反生效必需门槛；建议修复并验证后合并 |
| 中：建议处理 | 真实的功能、性能或维护影响，尚未构成高等级阻断；说明本次或后续处理的取舍 |
| 低：可选改进 | 有具体局部收益；无关紧要的偏好默认省略，不抢占主报告 |
| 待核实 | 缺场景、路径、规则或规模依据；不是低等级缺陷，只保留会改变判断的问题 |

先用一句话介绍需求，再说明整体完成情况和关键变化。每个正式问题应连起来说明：谁在什么条件下遇到、需求想怎样、代码现在怎样、后果与影响、位置和证据、最小处理或查明办法。区分可核查代码推导与真实运行，不编造复现。

用户举的“运营先修改源文再修改译文”仅作为本轮方法要求的例子，不当成已核实的国索项目事实。先查是否支持这种操作及真实入口；不能把想象的操作组合升级为必须修复。必要术语用普通话解释，例如说清重复回调怎样导致重复记录，不能只抛“缺乏幂等”。安全专项暂不增加，整体方案是否绕远路留在方案设计。

### 验证与迭代

1. 先检查角色配置、共享规则、链接与三专项调用。本轮用隔离快照验证行为，不修改业务项目；配置可读不等于生产效果已验证。
2. 再选真实变更，固定需求、代码版本、资料与工具，和原有 review 方法比较。样本应包含有问题和正常行为，避免把报得多当效果好。
3. 人工核对核心遗漏、误报、场景依据、说明能否看懂，以及阅读和执行成本。缺少真实用量时不估造成本。具体样本与效果门槛待定。
4. 从实际纠正提炼少量规则，保留适用范围及反例，复跑后用新样本检查。个人表达放通用要求，阶段方法放 Skill，业务规则留项目。

本轮小范围试跑已完成：三个专项分别使用独立上下文，显式传入完整角色指令；需求逻辑与架构专项验证了旧配置备份迁移、重复执行和新评审接入，性能专项未提出无依据的性能问题。首轮副本漏带上一轮未提交的关联文件，主会话补齐完整工作区并核对 40 个文件哈希后，两专项依据代码与临时目录验证关闭原发现。首轮结果不能作为实际仓库缺陷或误报率数据；此次仅验证配置内容、安装路径与基本报告行为，未验证原生角色调用和业务评审质量。

两位评审在独立上下文阅读原始材料后，各自形成判断并交换一次意见。共同建议是沿用现有骨架、从真实痛点验证；负责人也提醒：缺少反馈文档并不证明反馈机制就是使用瓶颈。用户随后选定代码评审焦点，因而细化本轮建议；之后用户进一步明确了三专项、独立上下文、分级及减少噪声的设计要求；这些后续要求取代此前待定的角色分工。
