# 代码评审

从实际变更判断合并风险，同时帮助维护者理解变更的运行路径、影响范围和关键取舍。合并决定由人负责。

## 确定评审方式与版本

- `$code` 在交付或创建 PR 前执行本地自查，修复本次范围内、证据明确的问题，并运行针对性验证。
- PR 阶段优先在独立会话或由独立评审者执行 `$review`。提供变更目的、验收条件、评审基线和相关规则，由评审者自行追踪实际代码与测试。作者的自查和验证记录可用于定位。当前会话兼任实现与评审时，在结果中说明。
- 明确评审范围与基线。评审 PR 时确认目标分支与实际 diff 的基线，记录 base 和 head 提交。读取与被评审版本一致的文件和测试。比较本地变更时检查暂存、未暂存和相关未跟踪文件，说明采用的基线。若 head 在评审期间变化，重核受影响的发现。

## 选择相关上下文并验证

1. **任务要求**。读取 PR 目的、工单、需求验收条件、设计和所评审的任务。核实预期行为、约束和异常场景。缺少会改变判断的依据时记录待核实项，继续检查有依据的风险。
2. **工程规则**。读取生效的 `AGENTS.md`、对应模块的团队标准和评审规则。按项目指令检查通用编码规范的可读路径，未配置时查看项目根目录的 `.agents/standards/coding.md`，再查看 `~/.agents/standards/coding.md`。按适用范围读取当次有效的规则，发现项引用文件与条目。规则或需求随 PR 变化时，核实基线版本、拟议变化和确认状态。
3. **实现与契约**。从变更符号和验收条件出发，用代码搜索、引用导航或已有索引定位完整实现、调用方、测试和契约。涉及接口、共享类型、事件或迁移时，按当前依赖版本追踪受影响的生产方和消费方。关联仓库不可读或版本无法核实时，说明具体缺口。
4. **验证风险**。先浏览整个变更，再按行为路径核对功能、架构、可读性、测试和受影响的系统约束。对关键假设检查旧数据、重复执行、权限边界和部分失败等相关场景。阅读断言，必要时运行已有的针对性测试，或从代码路径推导触发条件和结果。相同根因归为一个发现。
5. 大型、跨仓库或高风险变更，按需使用 [进阶评审](references/advanced.md) 的上下文检索和专项评审方法。团队要沉淀规则或比较评审效果时，也使用该参考。

## 风险分流

| 等级 | 使用条件 | 处理建议 |
| --- | --- | --- |
| 必须处理 | 有证据表明会破坏安全、数据完整性、关键行为或违反生效的合并门槛 | 修复并验证后再合并 |
| 需要人工审阅 | 实现与需求、契约或工程约束存在有依据的偏差，需确认业务意图或技术取舍 | 指出具体决定及其影响 |
| 低风险可修复 | 问题与收益明确，修改面小、容易验证 | 用户授权时做针对性修正并验证 |

将重要但缺少代码、契约或规则证据的疑点写入待核实项，指明缺什么以及如何核实。测试缺口须说明有实际风险的行为和缺失的断言。偏好类建议、与本次变更无关的存量问题和重复发现可省略。

## 输出与复查

1. 先按风险分流列发现。每项包含等级、`文件:行号`、触发条件、影响、证据，以及最小修复方向或验证方法。有对应要求时引用验收编号、规则条目、调用方或契约。没有发现时直接说明。
2. 简述入口、关键状态变化、受影响的调用方和兼容性。记录评审范围、版本、已执行的验证及结果，注明未覆盖的路径和待核实的判断。给出合并建议，说明是否有已知阻断项或需先核实的关键风险。
3. 用户追问或修复后复查时，重新读取对应版本的代码及契约，回答具体触发条件、受影响方和可验证证据。原发现只有在触发路径消失或验证证明行为符合要求时才关闭。
4. 评审默认只读。用户要求存档时，沿用已有工作项目录下的 `review.md`。修改代码、提交 PR 评论或合并均按用户授权处理。
