# 代码评审

帮助维护者理解本次要实现什么、代码是否做到、影响谁以及哪些问题值得处理。需求与逻辑正确性优先。通常组织三个独立专项，主会话负责统一材料、查证与汇总；合并决定由人负责。

## 先讲清需求与评审版本

1. 读取用户原话、工单或需求与验收，以及生效的项目指令。先用一句普通话说明：这次要让谁在什么场景下得到什么变化，哪些重要旧行为仍要保持。再列本次关键验收与边界；不以文件名或实现细节代替需求。不清楚时先查资料，仍会改变判断的歧义标为待确认，不擅自补成需求。
2. 确定实际 diff、base/head 或本地基线，包含相关暂存、未暂存和未跟踪文件。读取同版本代码、测试和直接上下游；作者总结与自查是线索，不代替源码证据。明确本次范围和既有改动；范围内新增的遗漏也要检查，不能只看改过的行。
3. 读取 `AGENTS.md`、模块规范与项目文档入口。通用规范按项目指定路径读取；未指定时检查项目 `.agents/standards/coding.md`，再检查 `~/.agents/standards/coding.md`。区分生效规则、拟议规则和个人偏好。
4. 准备中立材料：原始需求来源、验收与未知、真实入口和已有业务限制、版本与 diff、代码与规则路径、已运行验证。不要把实现者的倾向性结论当指令，也不要预先声称没有影响的模块已经检查。

## 三个独立角度

默认分工如下。职责是分工，等级是问题后果；任何专项都可能发现不同等级的问题。

| 角色 | 最重要的问题 | 查什么 |
| --- | --- | --- |
| `code_review_functional`：需求与逻辑 | 是否完整、正确地实现需求，旧功能有没有受影响？ | 主流程、真实边界、状态变化、调用方、历史数据、迁移或补跑、任务与接口联动、失败恢复和有效测试 |
| `code_review_architecture`：架构规范 | 改动是否放在合适位置，遵守已有边界和职责？ | 生效工程约定、模块依赖、类与方法职责、重复实现、已有扩展点、受影响契约及可维护性 |
| `code_review_performance`：性能 | 在实际使用规模下，是否新增有意义的耗时或资源问题？ | 查询与往返次数、循环内查询、重复计算或外部调用、全量扫描、大量更新、内存、并发、批量和后台任务 |

协调方式：

- 主会话把同一份原始材料与同一版本分别交给三位评审，使用独立上下文，不继承主会话结论、不读彼此初判。优先使用可用的原生角色；入口不可用时，读取对应 TOML 的完整 `developer_instructions` 并显式传入，注明兼容加载，不把同名子任务当角色加载成功。
- 专项子 Agent 读取本 Skill 的共享方法及[专项与举证细则](references/angles.md)，只执行自己的评审，不递归调度、不写评审文件、不修改业务代码。各自核对需求的一句话概括，需求理解不一致时汇总者先查明来源。
- 没有该专项的实质变化，可以检查后明确“未见相关影响”，不要求每人交出问题，也不因方法长就声称性能差。不新增安全专项；方案是否值得、是否应换路线交给设计或方向审查。
- 初判完成后主会话按根因去重、核查场景与等级。对具体冲突可定向补查一次，不通过多数票决定真伪。未解决的关键分歧说明缺什么材料，不冒充一致。
- 用户明确只要一个专项时按指定范围执行。工具或资源限制下可分批启动；只有同一会话分轮检查时，明确标注没有独立上下文。任一必需专项失败或未完成，报告“三专项评审未完成”，不得宣称整体已通过。

## 先查真实影响，再报问题

每个正式发现都要连起来说明：**需求或规则 → 触发场景及其依据 → 代码路径 → 实际后果 → 影响对象**。验证证据可来自可核查的代码推导或已运行测试，必须区分两者，不能编造复现。

- 边界来自支持的操作、真实入口、数据契约、已有数据或正常失败方式。对“用户先做甲再做乙”的推演，核对谁能操作、入口是否存在、业务是否支持；不能仅靠想象组合制造缺陷。用户明确不支持的操作不新增成验收条件；也不能仅凭界面没有按钮就断言服务、任务或数据写入方不可达。
- 低频不等于不重要：可达且会造成数据损失或关键流程错误的场景仍需报告。缺少可达性、使用方式或数据规模依据时列待核实，说明最小查明办法；不报成已确认缺陷。
- 只围绕本次新增、加重或阻碍本次目标的问题。存量问题标明来源和本次关联；风格偏好、无明确收益的重构、纯理论极端情况不列正式发现。
- 需求不完整时区分“代码违反已知要求”和“要求尚未确认”。测试缺口要指出具体漏测行为及其后果，不能只说覆盖率不足。

## 问题分级与证据状态

先判断后果，再判断证据是否充分。缺少证据不能靠降低等级混入正式发现。

| 等级 | 判定依据 | 处理含义 |
| --- | --- | --- |
| 高：必须处理 | 已有依据表明核心验收未实现、关键行为错误、数据会丢失或不一致，或违反生效的必需门槛 | 建议修复并验证后合并；说明具体受阻目标 |
| 中：建议处理 | 有可达路径和实际影响，损害非核心功能、合理规模的性能或明确的维护约束，但尚不构成上述阻断 | 说明影响与处理时机，由维护者决定本次修复或另排 |
| 低：可选改进 | 有清楚、局部的收益，当前行为正确且风险低 | 简短另列；默认省略无关紧要的偏好，不抢占主报告 |

“待核实”是证据状态，不是低等级。已查实也不等于已运行复现；注明代码推导、测试或数据来源。项目有已确认等级和门槛时沿用实际约定，保留对应含义。

## 面向人的报告与复查

报告先让人理解需求，再让人判断问题。使用普通中文和具体对象；符号名只用于定位，必要术语随文解释，不用“幂等、契约漂移、职责泄漏”等词替代因果说明。

1. **需求一句话与总体结论。** 说明目标是否实现、最重要差距或未核实之处。先给全局判断，再按高、中、低排序，避免先抛一长串局部名词。
2. **关键变化与影响。** 用短链路讲入口、状态或数据变化及主要受影响模块。资料不全时说明核实到哪里，不假装已看过全部上下游。
3. **值得处理的发现。** 每项以“等级＋具体后果”为标题；正文说明谁在什么条件下遇到、需求预期、现在代码会怎样、为何影响本次目标，附 `文件:行号`、必要规则或验收来源及最小修复/验证方向。不能只堆表格关键词。
4. **待核实与验证范围。** 记录版本、三个专项完成状态、已执行检查及未验证项；无发现时如实说明。无根据的设想不集中丢进“待核实”制造另一份噪声清单，只保留会改变判断的问题。

不强制代码评审正文套用方向审查的 300 字上限；简短开场，按问题补足判断所需的依据，不重复。示例与易误报情况见[专项与举证细则](references/angles.md)。大型变更、检索和规则迭代按需读[进阶评审](references/advanced.md)。

修复后重新核对对应版本、触发路径和验证，原问题只有在证据支持时关闭。默认只读；完整 workflow 汇总到同一工作项 `review.md`，单独评审仅在用户要求存档时写入。修改、PR 评论、提交和合并均按用户授权处理。
