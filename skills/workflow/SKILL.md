# 开发流程编排

## 确定范围和工作项

- 按用户明确指定的开始、结束和操作范围推进。只输入 `$workflow` 加原始需求时，默认先澄清需求、调查现状并设计方案，交用户确认；确认前不进入任务拆解和编码。用户明确要求直接实现、按已有方案实施或一次做到编码评审时，按已授权终点执行，不另设方案确认。只澄清、只拆任务、只实现指定任务或只评审时，采用对应范围。用户要求做到收尾或归档时，评审后进入 `$complete` 阶段。
- 读取项目指令，有 `AGENTS.md` 文档地图时，按入口读取与当前任务有关的规则和模块文档。按工单号定位进行中的工作项。发现已归档的工单时使用归档资料核对状态，只有用户要求继续处理时才执行相应操作。新建文档时采用项目约定，默认用 `docs/changes/<work-item>/`。先记录当前分支、工作区已有改动和适用的基线。指定 PR、diff 或代码时，可以用该变更作为评审入口。
- 续跑时查阅同一工作项已有的需求、设计、任务和评审记录，并查证当前分支、代码和验证结果。复用仍适用的产出，从第一个缺失或失效的阶段继续。已有评审结论仅覆盖记录中的 diff 或提交，后续变更应核查受影响的路径。需求或契约变化时只重做受影响的部分，保留原有效的验收和任务编号。

## 方案确认与继续

- 默认设计阶段可读取代码、按需调查和维护需求与方案文档；不修改业务代码、测试或迁移文件，不执行业务数据写入，也不启动编码执行者。需求澄清、角色选择和方案检查按 design Skill 完成，不要求用户提供一份完整模板才能开始。
- 默认流程中，设计达到可审阅状态后，用普通中文简述推荐方案、文档入口、待定事项及本次请求确认的实施范围，在此结束本轮，等待用户回复。已有文档、任务清单或方案评审通过均不代表用户确认；仍缺关键业务决定时，讲清影响、选项和建议。
- 用户针对当前方案回复“按这个方案做”“确认，开始实现”等，即可按确认范围继续任务拆解、编码、验证和代码评审，不再逐阶段或逐任务要求确认。仅补充需求、回答澄清问题或要求修改方案，不视为同意实施；用户只确认部分范围时，仅推进该部分。
- 在现有方案文档中简记实际确认依据和实施范围，未确认时保留待确认，不另建审批文档。续跑沿用仍有效的确认；确认后出现改变目标、范围或公共契约的实质变化时，只将受影响部分交用户重新决定，其他已获授权的工作继续。

## 组织各阶段

沿用各阶段 Skill 的内部流程。执行某阶段前，先确定总入口 `workflow/SKILL.md` 解析软链后的实际位置，再从同一个 `skills/` 目录打开对应的阶段文件，并按需读取相对于该文件的模板和参考资料。保持同一个工作项目录、用户约束和代码基线。交接时传递必要的文件路径、验收编号、任务编号、决策与阻塞。

| 阶段 | 使用的 Skill | 产出及交接条件 |
| --- | --- | --- |
| 设计 | [design](../design/SKILL.md) | 主会话澄清需求；按复杂度委派 `solution_designer`，按条件安排独立 `solution_reviewer`。统一维护需求与方案、验收、影响、验证和待定项；默认交用户确认后再拆解。 |
| 拆解 | [task](../task/SKILL.md) | 主会话按复杂度委派 `task_planner`，统一写 `tasks.md`；每项明确结果、范围与归属、前置实际产出、验收和完成证据。 |
| 编码 | [code](../code/SKILL.md) | 在已确认或明确获准的实施范围内，主会话直接实施或分配 `code_implementer`，先核对真实前置和写入范围；接收代码与验证证据后集成，在目标工作区核对整体验收。明确获准的小修可直接进入。 |
| 评审 | [review](../review/SKILL.md) | 针对指定 PR 或本次实际 diff，按 review Skill 组织需求逻辑、架构、性能三个独立专项，汇总有依据的发现、等级和验证范围。完整流程的结果写入同一工作项的 `review.md`。仅评审时沿用评审 Skill 的存档约定。 |
| 收尾 | [complete](../complete/SKILL.md) | 核对完成证据，判断主规格是否需要更新，归档工单并记录同步结果。 |

设计阶段的角色选择、资料交接和方案检查按 design Skill 执行，workflow 不再重复调度。简单需求可由主会话直接设计；只澄清不启动方案角色，只评方案不先另写方案。子 Agent 返回建议，主会话统一对接用户、修订正式文档，并把未决事项明确关联到受影响的验收与任务。方案评审和后续代码三专项评审分别记录，不能互相代替。

任务和编码的具体分工按 task/code Skill 执行。只拆任务不启动编码；简单工作由主会话直接处理。主会话明确每位执行者的任务、工作区、可写范围和共享约定，按实际依赖安排顺序；文件不同不自动意味着可并行。各执行者只改分配范围并交回证据，主会话统一维护任务状态，不让多人争写 tasks.md。

进入独立代码评审前，主会话确认各结果已在目标工作区集成、共享接口与数据一致，并对组合后的行为运行必要检查和核对原始验收。单项测试通过、独立分支已完成或子 Agent 的报告都不代替这一步。需要返工时按具体问题重新分配范围；已有检查只在相关变化或疑点需要时复跑。

每阶段核对实际产出，在用户已授权范围内继续推进；默认尚未确认的新需求到方案审阅处结束，不能因后续工作可执行而越过确认。缺少会改变业务行为或公共契约的决定时，记录受影响的阶段或任务并补充可判断的信息。技术依赖或验证环境受阻时，记录证据和解除条件，继续处理独立且已获授权的工作。

## 评审、返工和交付

- 明确评审基线与覆盖范围，结合开始时记录的改动区分本工作项范围。评审由当前实现会话执行时，标注为同会话评审。已有可用且获授权的独立评审者时，交接需求、实际 diff、版本和规则，让其自行核查。
- 完整流程发现本次范围内可修复的缺陷时，回到 `code` 修正并验证，再针对受影响路径复查。原因在需求或契约时，回到相应阶段，更新受影响的任务。只读评审、范围变更或需要业务决定时，记录发现和下一步所需信息。
- 完成时概括各阶段的实际产出、已运行的验证、评审结论和剩余阻塞。按用户授权处理提交、推送、创建或合并 PR、部署。
