# 任务拆解

把需求与方案落到有明确结果的工作，而不是文件修改清单。主会话维护正式 `tasks.md`、分配归属和处理决定；复杂拆解可由 `task_planner` 只读调查并返回建议。简单改动可以直接由主会话拆解。

## 范围与现状

- 读取适用项目指令、原始需求与有效验收、方案及检查意见，沿用同一工作项目录和编号。用户给出足够明确的改动范围与验收时可直接拆解，不为补齐流程重做方案。
- 核对代码基线、工作区已有改动、当前任务记录和实际验证。区分已完成、已有实现待验证、真正缺失和受阻的工作；不要重复安排已完成成果，也不只凭旧勾选认定完成。
- 只拆用户请求的范围。只要任务清单时到此交付，不写业务代码、不启动执行者。拆解发现方案缺少关键契约时，指出受影响部分及需补信息，不自行扩大设计或更改业务决定。

## 任务粒度与覆盖

1. 按可核对结果和完成条件拆分，例如一条业务路径、一次必要的数据处理或一组关键回归。小改动不强拆多个任务，大任务也不能笼统写“完成后端”。基础改动可以独立成项，但要说明谁依赖它、怎样验证。
2. 每项沿用稳定的 `T-01` 等编号，说明目的与预期行为、相关设计和验收编号、预计位置或搜索入口、前置产出及完成条件。路径已知时写路径或符号，未知时不编造位置。
3. 核对每条验收与方案必要改动都有对应工作，按相关性纳入历史数据、迁移/回填、配置、兼容性、上线顺序和验证；不能只列源码修改。列出操作任务不等于已获授权执行数据库写入或部署。
4. 一条验收可由多个任务共同完成。单项交付不自动完成整条验收；保留最终组合验证的安排，说明谁来核对实际集成结果。

## 可交给执行者的任务

使用[任务模板](assets/tasks.md)，按规模裁剪；小任务可以用短段，不为字段凑长文。交接材料应使新上下文能找到改动并判断完成：

- 任务编号、业务目的、原始需求和方案入口、相关验收及必须保持的行为。
- 当前代码基线、执行工作区或分支、已有改动和可复用成果。
- 允许修改的文件/模块及必要测试范围、负责者；不确定边界时先只读定位，再由主会话明确写入归属。
- 前置任务及其具体产出、相关共享接口/数据约定、预期结果与可观察的完成条件。
- 验证方式、预期结果和已知环境限制；影响本任务的待定事项及解除条件。

正式清单由主会话统一写入，子 Agent 不同时回填状态。任务规划者不得把自己的建议当人工决定或真实完成记录。

## 顺序、并行与阻塞

- 依赖按实际产出判断：接口、类型、配置、迁移或文件需要在执行工作区真实可用，不以“另一位说做完了”代替检查。
- 只有前置具备、写入范围与共享产出不会互相覆盖、公共约定已清楚时，才可并行。文件不同也可能通过接口、数据格式或生成物相互依赖；同一文件或同一契约的修改由主会话协调、拆范围或串行。
- 缺业务决定、资料、环境或外部依赖时，只标受影响任务为阻塞，写清证据、影响和解除条件。其他已有依据的工作可以继续；不编造验收门槛消除未知。
- 计划写清主要顺序和可并行理由，不预设任务数或为了展示并行而分工。需要独立工作区时标明后续由主会话集成；不要把独立分支上的完成误认为当前分支已具备产出。

## 状态与续跑

状态采用未开始、进行中、已实现待验证、已完成、阻塞；只有实际满足本任务完成条件才勾选。保留实际改动、检查命令与结果、版本和剩余问题；未验证不能写已完成。

更新时保留仍有效的编号、已确认事实和证据。需求、方案或代码变化时只重新核对受影响的完成状态，必要时拆分或标记替代关系，不静默丢掉旧要求。续跑先核对实际代码与记录，已有实现待验时先安排验证，不重新实现一遍。

## 角色与交接

主会话可把复杂拆解交给独立上下文的 `task_planner`，提供上述原始材料、基线和现状，不只给方案作者的摘要。子 Agent 只读并返回任务建议，不直接追问用户、不写正式文件、不递归委派。

优先使用可用的原生角色；入口不支持时读取对应 TOML 的完整 `developer_instructions` 并显式传入，说明兼容加载。无法独立委派时主会话直接拆解并如实说明，不把同名子任务当角色加载成功。

交付时先用普通话讲主要实施顺序，再给必要任务、可并行范围及具体阻塞。只请求拆解时结束；用户已授权后续实施时，将已具备条件的任务交给 code 阶段，保留尚待决定的部分，不新增逐任务审批门槛。
