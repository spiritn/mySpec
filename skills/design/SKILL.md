# 需求澄清与技术设计

读取项目指令和需求来源，复用已有工作项目录。新需求按项目约定建档，默认使用项目根目录下的 `docs/changes/<work-item>/`。有工单号时使用 `<工单号>-<短标题>`，否则使用简短语义名。

## 需求澄清

1. 从工单、PRD 或用户说明提取目标、范围和边界，按角色、触发条件、主流程和异常整理用例。区分现状证据和本次预期行为。
2. 将验收条件写成可观察的结果，使用 `AC-01`、`AC-02` 等编号。更新既有需求时沿用仍有效的编号。
3. 优先用现有材料和代码消除歧义。需要用户决定时，说明它会怎样改变业务结果、权限、接口或数据语义，并给出清晰选项。记录可逆假设，继续完成已有依据的部分。
4. 用 [需求模板](assets/requirements.md) 新建或更新 `requirements.md`。用户只要求澄清时，报告文档路径和待决问题后结束。已有明确需求且用户只要求设计时，直接引用现有文档或工单。

## 技术设计

1. 从实际入口追踪到相关实现和调用方。按需查看数据模型、配置、迁移、测试和上下游。用真实路径或符号说明现状、可复用能力与已知缺口。
2. 将验收条件映射到改动和验证方式。写清影响的模块、主要流程、状态变化、接口和数据契约。按改动范围考虑兼容性、权限、并发、重试、失败处理及可观测性。
3. 有实质取舍时比较可行方案的成本、约束和风险，给出选择及原因。对低风险且可逆的细节采用合理默认值。标明依赖待决事项的设计部分。
4. 用 [技术方案模板](assets/design.md) 写入同目录的 `design.md`，按改动规模裁剪。涉及接口变更、历史数据或部署顺序时写清验证和回退方式。核对方案对验收条件的覆盖、现状证据和失败路径。将具体实施任务交由 `$task` 生成。
