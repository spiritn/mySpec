# 需求澄清与方案设计

把原始要求、现状依据、候选方案与待定项讲清楚，形成可以交给任务拆解的方案。需求澄清由主会话对接用户；复杂设计可委派 `solution_designer`，独立方案检查由 `solution_reviewer` 承担。共同方法以本 Skill 为准。

## 范围、资料与文档

- 读取用户要求、适用的项目指令、已有需求及决定，保留其来源和日期。用户后来明确确认的变更优先；代码说明现状，不自动规定需求。开始时记录代码基线与已有工作区改动，禁止覆盖无关工作。
- 按用户指定范围执行：只澄清、只设计、只审方案或完成整个已授权流程。只澄清时不启动方案角色；只审已有方案时不先生成另一套方案；简单、明确、可逆的局部改动可以由主会话直接完成设计。
- 复用同一工作项目录，默认 `docs/changes/<工单号-短标题或语义名>/`。已有明确 PRD 或工单可原位引用，不重复抄写。通常只维护必要的 `requirements.md` 和 `design.md`；小改动可合并到项目已有文件。方案评审记在 `design.md` 内，不为每轮新建报告。
- 开头先用短段讲核心目标或方案，再展开判断所需的细节。普通中文，具体对象、流程与因果关系；必要术语随文解释。正文不套用方向审查的300字上限，也不靠加文件逃避精简。

## 需求澄清：由主会话负责

1. 先用一句普通话概括：谁在什么场景遇到什么问题，这次希望得到什么变化。再说明本次范围、重要旧行为和成功条件；不能用技术组件或文件名代替需求。
2. 分清用户明确要求、现状事实、假设与建议。按角色、真实触发入口、主要流程和有依据的重要边界整理用例，不为凑完整而新增不支持的操作或极端情节。沿用已有术语；影响含义的歧义要解释，不另造叫法。
3. 先查现有材料、代码和调用方。只把仍会改变业务行为、范围、公开契约或关键取舍的问题交给用户；说明为什么问、可行选项及各自影响，有依据时给建议。相互关联的问题合并问，优先解决会改变下一步的问题，不重复问已经确认或能够查明的事实。
4. 按可观察结果写验收条件，使用并保留有效的 `AC-01` 等编号。覆盖核心路径及相关重要边界，不把“新增某个类”当验收。需求调整时核对受影响的条件，不能静默删除原要求。
5. 允许待定。每项说明缺什么、为何影响决定、影响哪个验收或设计部分。可逆假设明确标注后继续独立工作；涉及关键业务决定时不替用户拍板。区分可设计部分与受阻部分，不要求所有未知都消失才做任何工作。

按需使用[需求模板](assets/requirements.md)。只要求澄清时，到此交付目标、范围、验收与必要问题，不继续编方案或代码。

## 技术设计

1. 从验收结果倒推必须成立的条件，再定位现有入口、数据、模块和调用方。按需查看配置、迁移、测试和上下游，说明哪些可复用、哪些必须改、哪些尚无依据，并引用文件、符号或现行文档。已有与计划新增的能力明确区分。
2. 先找最简单可行做法。有实质取舍时比较少量真正可行的选择，包含复用现有能力或最小改动；不要为凑数写多个方案。推荐方案说明收益、完整成本和风险，每个新增模块、抽象、依赖或中间步骤都应解释其实际作用。整体路线已获确认时尊重其范围；有反证可提调整建议，不自行更换目标。
3. 先讲整体链路和关键取舍，再说明改动位置、输入输出与责任。复杂链路可用短流程图。把每条验收关联到必要改动和验证，检查组合起来能否达成目标；任务级命令和逐文件施工清单留给 `$task`。
4. 按相关性核对接口与共享契约、数据读写方、历史记录、缓存、正常失败与恢复、实际规模下的性能和必要上线顺序。需要处理、不需要处理或尚待核实，都给理由；不默认每次都要迁移、回填或引入队列。对数据库结构、权限或对外行为的关键决定缺依据时，明确受影响部分。
5. 只调查会改变选择且现有材料查不清的外部问题，记录来源、版本与适用条件；不拿厂商案例代替本项目验证，不无限调研。缺工具或资料时报告具体限制，继续有依据的部分。
6. 按[方案模板](assets/design.md)整理推荐做法、整体链路、现状与复用依据、关键变化、取舍、验收覆盖、验证和待定项。文档按改动规模裁剪，没有内容的可选章节省略。

## 两个方案角色的调用

主会话负责澄清、调度与正式文件；子 Agent 只读调查并返回建议，不直接向用户重复提问、不递归调度、不写项目文件或业务代码。

| 角色 | 工作与输入 | 返回什么 |
| --- | --- | --- |
| `solution_designer` | 原始要求与已确认变更、验收和待定项、代码基线、材料与规则入口；深入现状并形成方案 | 推荐方案、整体链路、代码依据、复用与必要改动、取舍、验证和具体未知 |
| `solution_reviewer` | 同一原始资料、固定版本的需求与候选方案、代码与规则入口；先理解需求再独立核查方案 | 实施前须补齐的问题、需用户决定的事项、有收益的改进及关键待核实项；说明依据与影响 |

- 跨模块、有重要技术取舍、涉及历史数据或调查细节较多时，可把方案调查交给设计者；简单需求不强制开两个子 Agent。用户明确要求独立方案评审，或存在重要跨模块契约、数据处理与高成本取舍时，安排独立评审者。
- 设计者产出之后再交评审者检查。两者各用独立上下文，均获得原始要求和既有人工决定；不能只给设计者摘要。记录所依据的需求、方案及代码版本，不能拿旧方案评审结论覆盖后续修改。
- 优先使用可用的原生角色。入口不支持时，读取对应 TOML 的完整 `developer_instructions` 并显式传入，说明是兼容加载；同名子任务不等于已加载角色。若只能同会话自查，明确没有独立评审，不能冒充完成。
- 主会话统一核对事实和质疑，按原始要求及证据修订。针对具体问题最多一轮补查或受影响部分复核，不靠多轮互相赞成来结束；未解决的业务决定或材料缺口保留，不把同行支持当用户批准。

## 独立方案检查与交接

评审者按下面的方法检查方案；这同样用于未委派时的主会话自查。

- 对照原始要求和主要验收检查完整链路：必要步骤是否漏掉、关键前提是否有依据、接口与数据是否对得上、其他模块和旧数据怎样处理、怎样验证。现有代码可支持的部分与计划新增部分分别核对。
- 找能同样达成目标的更简单做法，解释省掉什么、付出什么。设计原则和模式只是检查线索；不能仅因没采用某种模式或为了未来想象需求要求重构。
- 每项意见说明问题、来源与触发条件、影响的目标或验收、查明或改进办法。区分“实施前必须补齐”“需用户决定”“可选改进”“待核实”；没有重要问题时可以支持，不能制造质疑。未核实的风险不是已证实缺陷。
- 先给整体判断，再给重要依据和意见。允许全部可拆解、部分可拆解或仍需澄清，并解释具体范围；这不是替用户批准实施。方案是否值得投入或业务目标是否正确，必要时交方向审查，不把它和实施方案检查混为一谈。

主会话在 `design.md` 简记检查人或方式、版本、重要意见、处理与未决事项。交给 `$task` 的资料须包含：原始需求入口、稳定的验收编号、方案与代码依据、影响范围及验证、可继续部分与具体阻塞。用户已授权完整流程且有可执行工作时继续推进，不新增“每阶段都等用户签字”的门槛；未授权实现时不修改业务代码。
