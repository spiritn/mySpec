# 项目决策记录

让用户在一张表中看清“要决定什么、建议怎么选、有没有确认、为什么”。允许长期待决策，按决策点维护，不按评审次数建档。

## 输入与权限

- 先读本项目 `docs/方向审查者/整体思路.md` 的目标、决策表及相关确认来源；已有同一决策点就更新原行。用户指定其他审查目录时沿用该目录。
- 只有用户明确的人工确认，或既有可核验的人工确认记录，才能标为已决策。AI 建议、双人一致、代码完成或试验成功均不自动构成确认。指令含糊时保留待决策，不把“要不试试”扩成主路线批准。
- 已决策可以是采纳、否决或暂缓；它不等于已执行或效果已验证。进展、验证结果分别写在同一份整体思路的对应章节。
- 仅在已授权范围维护文档。被委派的子 Agent 返回更新建议，主会话统一写入；不修改业务代码或擅自批准投入。

## 一张表的规则

使用[模板](references/templates.md)，嵌入 `整体思路.md` 的“决策记录”一节。固定五列：**决策点、描述、结论状态、论据、时间**。不创建 ADR 文件夹、单项 ADR 或独立决策总表。

- 决策点：一句话说明待选问题；已有 ADR 编号保留在这一格，便于追溯，无需新增编号列。
- 描述：简写主要选项及 AI 建议，避免把整段方案塞进表格。
- 结论状态：待决策／已决策／已替代。已决策须同时写实际决定及范围；待决策的建议留在描述列，不能装成结论。
- 论据：简写当时背景和关键证据；已决策还须注明人工确认出处。较长材料链接到已有来源或必要的调研材料，不另建决策说明文件。
- 时间：注明“更新”或“决策”及实际日期；未知写“未核实”，不把更新日当作确认日。

同一待决策问题更新原行。补充新证据不改写已决策事项当时的依据；重要补充可写入变更记录。重新挑战已决策事项时，在同表新增关联的待决策行，原决定保留；只有新决定经人工确认后，旧行才标为已替代，并注明承接它的决策点。迁移旧记录时保留已有编号、确认来源和历史关系，不能为了缩短表格丢掉决定范围。

## 表达与检查

用户日常只需打开整体思路；完整主文档不受 300 字总上限约束。顶部“当前判断”摘要及默认聊天审阅仍遵守总计 300 个可见字符、首段 100 个的上限，数字、条件和未知不能因压缩而失真。表内每格尽量用一两句短语；原始依据原位引用。具体格式遵循[文档契约](../project-requirements/references/document-contract.md)。

主文档写入后，从本技能目录执行：

```bash
python3 ../project-requirements/scripts/check_document.py /absolute/path/整体思路.md --overview
```

该模式检查顶部摘要及全文件的图形约束；另须人工核对五列表、确认来源及新旧决定关系。不要把主文档拆成多个文件来满足摘要字数。

`变更记录.md` 保留为一份文件，按日期追加重要证据、判断、计划或决定的变化；链接主文档章节或已有来源。不按天新建文件，不记录工具流水账或无变化运行，不重复抄写整张决策表。
