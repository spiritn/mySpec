# 项目调研

先说清“哪个问题的答案会改变哪项决定”，再选择调查深度。调研的价值是减少决策中的关键未知，不以资料数量或报告篇幅衡量。

## 输入与范围

- 读取项目原始目标、已确认变更、本轮决策及已有证据。项目目录不清楚且存在多个合理候选时再询问，不自行选择其他项目。
- 从 `docs/方向审查者/整体思路.md` 的目标、竞品／市场／方案调研、待定与验证、决策记录及其来源进入；已有调研优先引用，关键且可能变化的事实重新核查。
- 区分目标、约束、候选方案。用户没有确定的客户、市场、指标或预算，不替用户补成事实。

## 调查方法

1. 写出待查问题及其决策影响。优先调查会改变方向、投入顺序或验收条件的未知；无需为所有问题生成完整行业报告。
2. 发现当前环境实际提供的搜索、网页读取、文档或代码工具；有合适连接器时优先使用。不假设工具存在，不把角色说明当成工具授权。遇到认证或访问限制，说明缺口；可用其他公开来源补足时继续，不宣称已经读取受限资料。
3. 同时查找支持、反证和真正可行的替代方案。来源优先追溯到原文、现行实现或可复现实验；仍需检查方法、样本、版本和利益关系。官方材料、开源代码和某个工具的返回值都不自动等于已验证事实。
4. 对比必须说明共同目标与条件。竞品区分公开能力、推测实现和未披露细节；技术区分“接口存在”“链路实际使用”“效果已实测”；商业问题区分节省、完整增量成本与净收益。
5. 对每项重要依据记录来源、发布或版本信息、实际查阅日期及适用条件。来源冲突时保留冲突；未找到资料不等于不存在。外部成功案例不能代替本项目验证。
6. 证据足以支持本轮有限判断时结束。不能查明时写出缺口、对结论的影响和最小验证建议，不为了给出确定结论而编造数据或无限搜索。

安索夫矩阵、五力、失败预演、外部参照等只在问题需要时使用。失败预演产生的是假设；不能把想象的风险写成已经发生的事实，也不必在输出中列方法名称。

## 产出与写入

使用[模板](references/templates.md)，把调研写成可向同事介绍、向老板汇报的文字。章节按项目称为“竞品调研”“市场分析”或“方案调研”，不机械使用“当前依据／主要缺口与取舍”等审查表头。先把别人是谁、做什么、怎么做、取得什么结果讲清楚，再说明与本项目有关的未知和借鉴点；不只列出我们自己的候选路线。

竞品适合每家用一个小节、几个短段：产品与推出时间、核心做法和技术、公开成果及条件、关键未披露信息。推出时间与文章日期、首发与后续升级分开；不知道首发就说明目前最早查到的公开介绍日期。技术描述区分模型与业务用途、选区方式、编码标准与实际编码器实现，不从“大模型”“支持H.265”等说法补猜内部架构。效果数字写明厂商口径、比较对象和场景，未公开的核心细节可直接写“所查资料未披露”。具体字段随项目需要取舍，不把技术竞品结构套给所有市场问题。

调研介绍、结论和未知项写回 `整体思路.md` 对应章节，让用户在同一文档中审阅；详细来源按需链接。完整主文档不套 300 字上限；顶部“当前判断”摘要与默认聊天审阅最多 300 个可见字符，首段最多 100 个且计入总额。保留会改变判断的数字、条件和未知，不为控制摘要字数增建文件。统一格式遵循[文档契约](../project-requirements/references/document-contract.md)。

主文档写入后，从本技能目录运行 `python3 ../project-requirements/scripts/check_document.py /absolute/path/整体思路.md --overview` 检查摘要及全文件图形约束。专项材料不传 `--overview` 或 `--brief`，仅检查图，并人工核对主要章节先讲清本节要点。只有已授权写入时才修改文件。

- 结果按已知、推断、未知表达，不强制得出支持或反对结论。
- 需要持久维护的专项证据才写入 `调研/`；优先更新同主题材料，不为每轮审查新建报告、索引或来源摘要。只回答一个小问题时直接更新主文档。原始实验结果、代码和外部资料保留原位并链接。
- 未解决问题维护在整体思路的待定与验证一节；涉及决定时用 `project-adr` 更新同文档的五列表，不新建 ADR 目录。被委派的子 Agent 只返回资料和建议，由主会话统一写入。
- 不执行训练、转码、部署、购买、联系客户等行动；不把调研结果当成用户批准。
