# 项目需求与方向审查

从用户原始目标及明确确认的变更出发，维护简洁、可追溯的项目全貌。允许暂不决策、探索和反复验证；不为完整而编造指标或阶段。

## 输入与输出

确定项目根目录、本轮问题和材料入口；一个业务项目可以覆盖多个仓库。优先读取已有项目约定与原始来源，只追问会改变判断且无法从材料查明的问题。

默认工作目录为项目根目录下的 `docs/方向审查者/`，已有目录沿用用户指定位置。先读[文档契约](references/document-contract.md)，用[模板](references/templates.md)维护一份 `整体思路.md`：目标背景、必要术语、竞品／市场／方案调研、方案与进度、待定与验证、内嵌决策表。另留一份按日期追加的 `变更记录.md` 和按需使用的 `调研/`。不再按这些章节拆文件，不建 ADR 目录、单项 ADR 或单独的总览入口。原始资料原位引用。

区分原始要求、用户已确认变更、现状事实、候选方案和假设。推测的“本质需求”不得覆盖用户原话。已选路线、执行进展、效果验证分别记录。当前文档之间有冲突时保留来源与日期，不用较新的AI总结自动覆盖明确的用户决定。

## 需求定义与拆解

说明谁遇到什么问题、成功时应看到什么结果、约束和本轮范围。数值门槛没有确认时标为待定，可另提出建议门槛。术语只解释影响理解的词，沿用用户和项目的已有叫法；解释业务含义和容易混淆的边界，不另造概念或另建术语文件。

按可单独判断或验证的问题拆解。每步说明对总目标的作用、输入/依赖、预期结果、通过条件与未知项；近期具体，远期允许待定。复杂问题用至多7个节点的主链路图展示并行和依赖，假设关系用虚线并标“待验证”。不得把开发命令或代码清单当成方向拆解。局部通过后仍检查组合结果和累计成本/损失。

## 正式双人审查（由主会话调度）

若本次仅整理需求或文档，不必额外启动正式评审。用户要求方向/路线/可行性正式审查时：

1. 准备中立材料包：原始要求、用户确认、当前候选方案、证据及其出处。第一轮不传上次评审意见或另一位的结论；必须保留已确认的历史决定与限制。
2. 按预定义角色启动 `project_director` 和 `independent_reviewer`，使用独立上下文，禁止继承主会话的倾向性结论。两人返回初判和来源，子Agent不得继续递归启动评审。
3. 两份初判都完成后，交换关键质疑，最多一轮补查。以新证据或明确推理修正解释改判；保留未解决分歧。任何一位失败都标记“双人审查未完成”。
4. 主会话汇总并单独写入审查目录。使用 `project-research` 补查关键未知；使用 `project-adr` 提出/记录决定。双人一致不是用户批准。

当前接口若不支持选择预定义角色，不得把子任务取同名当成已加载配置。可读取对应TOML并显式传入完整角色指令作为兼容方式，但必须标注“显式加载指令，非原生按名调用”。用户要求原生调用时优先使用已经验证的原生入口；不可用就报告限制，不伪造成功。

## 面向人写作

整体思路是给人介绍项目、与同事交流和向老板汇报的文档。先讲具体对象怎么做、为什么有用，再讲取舍与未知；避免用“当前依据、主要缺口”等审查标签代替对方案本身的介绍。

调研章节按项目选名：竞品调研、市场分析或方案调研，沿用用户认可的叫法。竞品按厂家／产品讲清推出时间、做法、核心技术与亮点、公开成果，以及影响我们方案的未公开细节；篇幅较长时每家一个短小节。发布日期与首发时间、厂商数据与独立实测、公开标准与实际实现分别说明，细节见 project-research。

## 验收输出

聊天中的审阅正文、子 Agent 的判断，以及 `整体思路.md` 开头的 `## 当前判断` 均≤300个可见字符，首段≤100且包含在300内。整份主文档不套用300字限制；各节简写，详细证据优先引用已有资料，必要时放入已有主题的调研文档。不得为了控字拆出更多管理文件，也不得删掉会改变判断的条件。

写后执行；“本技能目录”使用当前 SKILL.md 所在目录的实际路径：

```bash
python3 "<本技能目录>/scripts/check_document.py" "<整体思路.md绝对路径>" --overview
```

`--overview` 检查开头摘要及全文图形；独立短答使用 `--brief`，专项资料不加这两个参数。检查器不证明推理正确；还须核对来源、未知项、人工确认、链接和整体因果关系。整理旧目录时先备份，再合并有效内容、修正引用并移除已合并文件；不抹掉原始资料和决策历史。

技能只授权完成当前请求范围内的文档工作，不授权修改业务代码、运行重型实验、部署、提交、推送或创建定时任务。
