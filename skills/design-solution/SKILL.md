# 技术方案设计

1. 读取项目指令、需求来源和同一工作项的 `requirements.md`（如有）。核对目标、范围和验收条件。已有简短工单且足以设计时直接使用，保留原始依据。需要业务决定的问题与技术假设分别记录，只阻塞依赖该决定的设计部分。
2. 从实际入口追踪到相关实现和调用方。按需查看数据模型、配置、迁移、测试和上游下游。用真实路径或符号记录现状、可复用能力与已知缺口。外部依赖的行为缺少证据时明确标记。
3. 将验收条件映射到改动、涉及模块和验证方式。描述主要流程、状态变化，以及受影响的接口、数据和错误契约。对代码改动的范围具体到模块、文件或符号。按需要讨论兼容性、权限、并发、重试、部分失败与可观测性。
4. 有真实取舍时列出可行方案，对比与本需求相关的成本、风险和约束，推荐其一并说明原因。对可逆的细节给出合理默认值。仍需用户决定且影响交付目标或重大契约的事项单独标记。
5. 用 [design.md 模板](assets/design.md) 写入工作项目录。优先使用已有 `requirements.md` 所在目录或项目约定，默认用 `docs/changes/<work-item>/design.md`。按改动规模裁剪章节。实施步骤按依赖排列，由可验证的功能切片组织。涉及接口契约、历史数据或部署顺序时写清验证与回退方式。
6. 核对每条验收条件的验证映射，检查现状证据、失败路径和方案冲突。只做设计时，以方案路径、主要决策和待决事项收尾。
